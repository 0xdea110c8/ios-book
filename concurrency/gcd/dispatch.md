## Dispatch
### Описание
`Dispatch framework` позволять планировать блоки на асинхронное и конкурентное выполнение методами, описанными в [DispatchQueue.async](#dispatchqueueasync)
и dispatch_apply.  
[Dispatch queues](#dispatchqueue) - это базовые юниты организации блоков. Несколько очередей создаются по умолчанию, приложения могут создавать
дополнительные (см. dispatch_queue_create).   
`Dispatch groups` позволяют приложениям отслеживать прогресс выполнения блоков, отправленных в очереди, и совершать действия 
по завершении выполнения блоков (см. dispatch_group_create).  
`Dispatch framework` так же предоставляет методы для отслеживания системных событий и автоматической отправки обработчиков событий
в dispatch queues.
## DispatchQueue
### Описание
В `Dispatch` очередь - это объект, который управляет отправленными в неё задачами. Блоки, отправленные в очередь, исполняются в порядке FIFO на пуле тредов, управляемым системой. 
>[!IMPORTANT]
>Кроме `main` очереди, которая использует главный тред, система не гарантирует, на каком треде любая другая очередь будет выполнять блоки.

Очереди могут быть последовательными и конкурентными.
### Serial queue
Последовательная очередь выполняeт блоки по одной в порядке FIFO.
```
┌────────┐┌──────────────┐┌──────────┐┌──────────────────┐
│ Блок 1 ││ Блок 2       ││ Блок 3   ││ Блок 4           │
└────────┘└──────────────┘└──────────┘└──────────────────┘
```
>[!IMPORTANT]
> Сериализация блоков работает только внутри одной очереди. Очереди исполняют блоки конкурентно по отношению друг к другу.
### Concurrent queue
Конкурентная очередь так же выполняет блоки в порядке FIFO, но может начать выполнение следующих блоков до завершения уже запущенных.
```
┌────────┐
│ Блок 1 │
└────────┘
  ┌──────────────┐
  │ Блок 2       │
  └──────────────┘
      ┌──────────┐
      │ Блок 3   │
      └──────────┘
        ┌──────────────────┐
        │ Блок 4           │
        └──────────────────┘
```
Количество блоков одновременно выполняемых очередью, зависит от многих факторов
- Остальные процессорные ресурсы могут быть заняты другой работой.
- Другие блоки этой очереди могут быть ещё не готовы к выполнению.
- Другие блоки могут ждать блокировку.
- Выполнение может быть ограничено семафором.
- Сейчас выполняется барьерный блок.
- Для данной очереди в данный момент времени может быть доступен только один поток
- На планирование может влиять приоритет, текущая нагрузка, энергосбережение и температурные ограничения.
> [!IMPORTANT]
> Таким образом, конкурентная очередь вообще не гарантирует параллельное выполнение блоков.
### Преимущества очередей над потоками
- Не нужно писать код для управления потоками, система сама занимается этим, справляясь эффективнее.
- Система может динамически масштабировать количество потоков в зависимости от доступных ресурсов и текущих системных условий.
- Система обычно начинает выполнение задачи быстрее, чем при ручном создании потока.
- Синхронизация доступа к ресурсу последовательной очередью эффективнее так как не требует вызова ядра.
- Очереди не блокируют используемые потоки.
## Проблемы избыточного создания потоков
Из документации [DispatchQueue/Avoiding Excessive Thread Creation](https://developer.apple.com/documentation/dispatch/dispatchqueue#Avoiding-Excessive-Thread-Creation):  
При проектировании задач для параллельного выполнения следует избегать вызова методов, блокирующих текущий поток. Когда блок, запланированный в очереди для параллельного выполнения, блокирует поток, система создает дополнительные потоки для запуска других блоков из очереди. Если слишком много задач вызывают блокировку, в приложении может возникнуть нехватка потоков.

Еще одной причиной чрезмерного потребления потоков является создание слишком большого количества собственных очередей диспетчеризации для параллельного выполнения. Поскольку каждая очередь потребляет ресурсы потоков, создание дополнительных параллельных очередей усугубляет проблему их избыточного расхода. Вместо создания собственных параллельных очередей передавайте задачи в одну из глобальных очередей диспетчеризации для параллельного выполнения. Для задач, требующих последовательного выполнения, следует назначать целевой очередью для своей последовательной очереди одну из глобальных параллельных очередей. Это позволит сохранить последовательный порядок выполнения задач, минимизировав при этом количество отдельных очередей, требующих создания потоков.
## DispatchQueue.async
### Описание
Методы `DispatchQueue.async(group:qos:flags:execute:)` и `DispatchQueue.sync(group:qos:flags:execute:)` планируют блоки для конкурентного выполнения 
в фреймворке `Dispatch`. Блоки отправляются в очередь, определяющую политику их выполнения.
(см. dispatch_queue_create).  
Эти методы поддерживают эффективные временные блокировки, фоновое параллельное выполнение и
параллельное выполнение на уровне данных. Эти же методы могут быть использованы для эффективного уведомления о завершении асинхронных блоков (aka коллбэки).
### Временная синхронизация
Синхронизация часто требуется когда несколько потоков выполнения получают конкурентный доступ к общим данным. Простейшая форма синхронизации - взаимное исключение (блокировка), при
этом различные подсистемы выполняются конкурентно до момента входа в критичную секцию.  
В семействе `pthread` временная блокировка достигается так:
```
int r = pthread_mutex_lock(&my_lock);
assert(r == 0);

// critical section

r = pthread_mutex_unlock(&my_lock);
assert(r == 0);
```
Метод `DispatchQueue.sync(group:qos:flags:execute:)` может быть использован вместе с последовательной очередью для 
достижения того же стиля синхронизации, например:
```swift
myQueue.sync {
     // critical section
}
```
Помимо более лаконичного выражения синхронизации, этот подход менее подвержен ошибкам,
поскольку критичная секция не может быть случайно покинута без возвращения в состояние,
допускающее повторный вход. Отложенная критичная секция имеет те же свойства синхронизации как и код выше, но является неблокирующей и поэтому более эффективной в 
выполнении, например:
```swift
myQueue.async {
     // critical section
}
```
### Фоновое параллельное выполнение
Метод / `DispatchQueue.global(qos:).async(group:qos:flags:execute:)` может быть использован для выполнения простых фоновых задач на глобальной конкурентной очереди, например:
```swift
DispatchQueue.global(qos: .default).async {
     // background operation
}
```
Этот подход является эффективной заменой `pthread_create`.
### Коллбэки по завершении
Коллбэки по завершении могут быть реализованы посредством вложенных вызовов в метод `DispatchQueue.async(group:qos:flags:execute:)`.  
В ARC при работе с пользовательской очередью необходимо обеспечить сильную ссылку на неё на протяжении всего времени, пока она нужна. 
```swift
func executeOnQueue(
    block: @escaping @Sendable () -> (),
    completion: @escaping @Sendable () -> (),
    destinationQueue: DispatchQueue
) {
    myQueue.async {
        block()
        destinationQueue.async {
            completion()
        }
    }
}
```
### Рекурсивные блокировки
Хотя метод `DispatchQueue.sync(group:qos:flags:execute:)` может заменить блокировку, он не может заменить рекурсивную блокировку. В отличие от блокировок, очереди поддерживают как асинхронные, так и синхронные операции, причем эти операции упорядочены по определению.  
Рекурсивный вызов метода `DispatchQueue.sync(group:qos:flags:execute:)` приводит к простой взаимоблокировке, поскольку выполняющийся в данный момент блок ожидает завершения следующего блока, а следующий блок не может начаться, пока не завершится текущий.

В процессе проектирования фреймворка `Dispatch` Apple изучала рекурсивные блокировки. Выяснилось, что подавляющее большинство таких блокировок внедряется задним числом — уже после того, как обнаруживаются проблемы с отсутствием четкого определения иерархии блокировок. Как следствие, использование рекурсивных блокировок часто превращает очевидные баги в трудноуловимые. В ходе исследования также выяснилось следующее: если
повторный вход неизбежен, то `reader/writer` блокировки предпочтительнее рекурсивных блокировок. Грамотное использование `reader/writer` блокировок позволяет допускать повторный вход лишь тогда, когда это безопасно (в режиме чтения).

Тем не менее, если это совершенно необходимо, ниже приведен неидеальный способ реализации рекурсивных блокировок с использованием фреймворка `Dispatch`:
```
func sloppyLock(object: Object, block: () -> Void) {
    if object.owner == pthread_self() {
        block()
        return
    }

    object.queue.sync {
        object.owner = pthread_self()
        block()
        object.owner = nil
    }
}
```
Приведенный пример не решает проблему, возникающую, когда очередь A выполняется в потоке X и вызывает `DispatchQueue.sync(group:qos:flags:execute:)` для очереди B (выполняющейся в потоке Y), а та, в свою очередь, рекурсивно вызывает `DispatchQueue.sync(group:qos:flags:execute:)` для очереди A, что приводит к взаимной блокировке. Это вплоть до ошибок совместимо с нетривиальным использованием потоков. На самом деле, полноценную реентерабельность невозможно поддерживать с помощью рекурсивных блокировок, когда реентерабельность достигает своего предельного уровня — IPC (Inter-Process Communication) или RPC (Remote Procedure Call).

### Неявные ссылки
Синхронные методы в рамках фреймворка `Dispatch` обладают неявной ссылкой на целевую очередь. Иными словами, синхронный метод заимствует ссылку у вызывающего метода (это допустимо, поскольку вызывающий метод заблокирован в ожидании результата выполнения синхронного метода и, следовательно, не может изменить счетчик ссылок очереди до тех пор, пока синхронный метод не завершит работу).

Это отличает их от асинхронных методов, которые должны держать как блок так и очередь в
течение всего времени выполнения, так как вызывающий метод может сразу отказаться от использования этих объектов.

### Основы
Концептуально `DispatchQueue.sync(group:qos:flags:execute:)` представляет собой удобную обертку над `DispatchQueue.async(group:qos:flags:execute:)`, дополненную семафором для ожидания завершения блока и оберткой вокруг самого блока, сигнализирующей о его выполнении. Дополнительную информацию о семафорах в `Dispatch` можно найти в описании dispatch_semaphore_create. Фактическая реализация функции `DispatchQueue.sync(group:qos:flags:execute:)` может быть оптимизирована и отличаться от приведенного выше описания.
